ROCm or Vulkan on an AMD iGPU: the fix, and the race.

My mini PC said a 12B model didn't fit. ROCm could only see 7.6 GiB of a machine with 16 GB set aside for graphics. One kernel boot setting fixed it - and then I timed both backends.

7.6 → 12GiB ROCm can use, one boot setting
23.6GiB Vulkan saw all along
~221-231tok/s ROCm reads prompts (Vulkan 146-194)
+7-10%Vulkan writes faster

Part 2 · the symptom

"Doesn't fit" - over a 126 MiB buffer

In September, Ollama refused to start a 12B model on this machine:

ggml_gallocr_reserve_n_impl: failed to allocate ROCm0 buffer of size 132137216

That is 126 MiB, on a 32 GB machine. The fix at the time was to switch Ollama to Vulkan. This page is about why it happened, and how to fix ROCm itself.

Part 2 · two pools

Integrated graphics borrow from RAM - in two pools

The firmware sets aside 16.0 GiB as video memory. Linux adds a shared pool (GTT) the graphics driver can map on demand: 7.6 GiB by default. On this machine:

backendwhat Ollama's startup log reportswhich pools
Vulkantotal "23.6 GiB"video memory + shared
ROCmtotal "7.6 GiB"the shared pool only (equals it on both boots I measured)

Why 7.6? Linux sizes the shared pool (the ttm.pages_limit kernel setting) at half the RAM left after the video memory: 15,604 MiB ÷ 2 = 7,802 MiB. Here pages_limit was 1,997,339 pages × 4 KiB = 7,802 MiB. A live change of that setting does nothing - the pool is sized when the driver loads - so the fix is a boot parameter.

Part 2 · the fix

One kernel boot setting

I raised the shared pool to 12 GiB: pages = GiB × 262,144 (4 KiB pages) → 3,145,728.

GRUB_CMDLINE_LINUX_DEFAULT="... ttm.pages_limit=3145728 ttm.page_pool_size=3145728"
sudo update-grub && sudo reboot

After the reboot the shared pool was 12.0 GiB; ROCm reported 12 GiB and Vulkan 28. The 12B loaded on ROCm with 49/49 layers on the GPU.

Leave room for the system. This box has no swap; the shared pool is a ceiling, not a reservation, but anything that trusts the bigger number can now ask for more RAM than exists. I keep one big model loaded at a time.

Or skip all of it: Vulkan already sees both pools, no reboot. In Ollama it is one line (a systemd drop-in here):

Environment="OLLAMA_LLM_LIBRARY=vulkan"

To see what your own backend can use, read Ollama's startup log:

journalctl -u ollama | grep "inference compute"

Part 3 · the race

ROCm reads faster. Vulkan writes faster. ROCm finished first.

Reading a prompt is compute-bound - ROCm stays flat around 226 tok/s while Vulkan climbs with length. Writing is bandwidth-bound - every token reads the whole 7 GB model from RAM, and on this chip Vulkan runs close to the memory's limit. The last column is computed, not measured: the answer length (tokens) past which Vulkan's faster writing wins back the time ROCm saved reading.

The rule on this machine: agents (big context, short replies) → ROCm. Long chat answers → Vulkan, which also needs no reboot. One model, one machine - test yours.

Short-prompt check, 256-token answers, 3 runs each: ROCm 10.62 · Vulkan 11.32 · Vulkan on the default boot 11.30 tok/s - the boot setting does not change Vulkan.

Open questions

Why does ROCm write slower?

Vulkan put the model in the video memory; ROCm can only use the shared pool. So I forced Vulkan into host memory (GGML_VK_PREFER_HOST_MEMORY=1) with a ~3.9K-token prompt:

armread tok/swrite tok/s
A ROCm218.69.83
B Vulkan184.310.73
D Vulkan + host memory165.310.51
Placement explains about a quarter of the writing gap, if the setting moved the buffers at all - Ollama's log labels them the same either way. What is the rest: ROCm's kernels for gfx1150, or how the shared pool is mapped?
Is "ROCm only uses the shared pool" by design on these chips, and is a small firmware carve + a large shared pool the intended setup? On this machine ROCm's total equalled the shared pool on both boots.

Tell me in the comments of the post, or open an issue on the repo.
